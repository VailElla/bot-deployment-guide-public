# ASR 与消息调度方案

这是一套 Windows + SnowLuma + AstrBot + 本机模型桥接的**定制实现参考**，整理自 2026 年 10 月下旬的部署和验证。数字是该次实现的配置或上限，不是 AstrBot、QQ 或模型的默认值，也不保证适用于其他硬件。仓库现提供[本地 ASR 组件](../components/local_asr/README.md)；完整桥接、队列、语音适配与模型仍未发布。部署者应重新核对版本、硬件、插件及当前配置，并对音频处理征得使用者授权。

不同阶段具体使用的模型与语音采样参数见 [模型方案](model-stack.md)。

多条消息交错到达时的会话锁、触发边界与上下文组装细节见 [多消息与上下文方案](multi-message-context.md)。

## 从消息到回复

```text
QQ 事件（记录平台、机器人、会话、发送者、消息与引用）
   ├─ 文字 ───────────────────────────────┐
   └─ 语音 → QQ 原生转写                   │
                └─ 失败 → 已配置的 STT     │
                     └─ 失败 → 本地 ASR ──┤
                                           ↓
             按会话组装上下文 → 同会话锁 → 文字模型并发许可
                   → 模型与工具 → 保存生成历史、释放会话锁
                   → 同群交付顺序 → 可选 TTS 队列 → 发送与回执
                                      └→ 合成失败时文字回退 ──┘
```

这是各阶段的逻辑示意，并不表示所有平台、私聊或流式回复都使用相同钩子。输入转写、文字模型、输出 TTS 与发送是不同资源：一个阶段能并发，并不代表其他阶段也能并发。请求的实际等待是多个阶段和可能的重试之和；只有覆盖相同范围的计时才能比较。

## 输入语音：三级转写和来源归属

1. **QQ 原生优先**：对有对应消息 ID 的语音调用平台转写。示例实现允许最多三次尝试，重试间隔为 1 秒和 3 秒；锁等待、调用及间隔共用 23 秒原生阶段预算，异常仅对可重试错误重试。相同消息的并发原生请求使用同键锁与短期成功缓存，避免互相替换。多条语音不能共用第一条语音的转写结果。
2. **已配置 STT 次之**：若框架配置了兼容的语音识别提供商，原生失败后尝试；未配置时直接跳过。示例设置单独的 23 秒等待上限。外部 STT 会形成额外数据流，需明确授权与隐私边界。
3. **本地 ASR 兜底**：QQ 媒体经接入层转换为 WAV；本地适配校验配置、引擎和模型，然后排队、转换和识别。示例采用 Qwen3-ASR-0.6B 的 Q4_K_M GGUF、CLI 按需启动，不是常驻识别服务；语言为自动识别。换模型或量化版本需另测可用性、资源占用和准确率。
4. **保留归属**：直接语音属于本轮发送者，引用语音保留被引用消息及原发送者的关系，不把引用内容拼成当前发送者亲口说的话。成功文本才能进入对应上下文；失败或内容不完整时应说明未能取得内容，不能猜测。

该示例在唤醒检查前处理直接和引用语音，以便保留语音里的唤醒词；最多对一个事件中的前 5 个语音组件并发发起处理，之后的组件标记为未取得转写。并发发起不等于本地 ASR 并行执行：同一消息的原生调用和本地共享模型仍分别受锁约束。原生缓存的示例有效期为 10 分钟、最多 256 条；应按隐私需要调整并验证会话边界。

示例中原生阶段、可选 STT 与本地阶段各有独立预算，并非整个语音输入只有 23 或 45 秒。全部失败可能造成更长等待。一次真实故障中，原生转写失败，本地识别的非静音首段也返回空文本；音频收到不等于转写成功。更大模型尚未完成对照或切换生产，强制语言也不能自动解决识别错误。

## 本地 ASR 的共享锁、切片与预算

输入语音回退、视频音轨和生成语音的输出复核共用同一模型与跨进程文件锁。不同插件、进程或热重载后的实例都要持有该锁才能进行受保护的转换与识别；示例同一时刻仅处理一项，等待锁的时间计入各自预算。文件锁提供互斥，不应假设它保证严格 FIFO 或所有等待者都会在期限内执行。QQ 输入适配还使用自身的异步锁；锁与模型全局并发许可不是同一把锁。

本地输入示例为最长 300 秒、32 MiB，整个本地阶段 45 秒，包括校验、等待、解码与识别；上限不意味着 300 秒音频一定能在 45 秒内完成。视频示例上限 180 秒，音轨转写预算 40 秒，视频整体处理预算 90 秒；输出复核示例 180 秒、40 秒总预算。各预算以各适配实际覆盖范围为准，不能与 TTS 合成期限混用。

音频归一化为 16 kHz、单声道、16 位 PCM；按最多约 25 秒的片段切分，在边界附近选择低能量点，按顺序连续覆盖全部采样点。低于配置阈值的静音片段跳过；非静音片段若识别为空或失败，则整次标记失败，不静默丢弃。转写结果按片段顺序合并并限制输出长度。静音判定可能漏掉很轻的语音，需要用真实样本调阈值；自动语言识别也可能识别错或重复，空值检查不能证明逐字准确。

每次处理使用独立临时目录。取消、超时或错误时终止当前识别子进程、等待清理并释放锁；诊断应区分锁等待、转换、识别与结果读取，避免保存音频和正文。恢复后用新请求确认锁没有遗留，不能通过无限延长超时掩盖卡死。

## 文字模型并发与同群顺序

该次桥接允许最多 **4 个跨会话模型请求**同时取得提供商许可，第 5 个等待；普通请求以 120 秒预算覆盖提供商排队、媒体准备、模型生成与受限重试。部分特殊任务可能采用不同期限，须按实际代码检查。前置语音识别、原生会话锁、语音合成与交付不一定包含在该提供商预算内；更大的并发上限不保证模型服务、GPU 或网络真的能同时完成四次计算。

同一会话使用原生会话锁，群聊模型和工具流程保持串行，避免两个请求同时修改同一份历史；不同群或会话可争取全局许可。群聊的持久线程按可信会话键隔离，清空历史、模型变更或会话失效时重建。工具工作区仍按本轮真实发送者授权，不能因为群共享历史而共享文件权限。

仅在明确识别为可重试的容量错误、且本轮没有回答输出和工具副作用时，可在原期限内有限重试；例如群聊常驻路径额外尝试一次。取消、超时、已有部分输出或工具动作时不能盲目重放整轮，避免重复发消息或执行操作。其他路径的重试次数可能不同，应单独核验。

## 同群有序交付与 TTS

对该实现支持的普通、非流式群聊，本轮模型与工具完成并保存历史后释放会话锁；随后进行结果装饰、语音合成和发送。下一轮可在上一轮交付期间开始模型生成，但两个同群模型阶段仍串行。交付票据在会话锁内分配，同群依次处理；最多 8 条待交付，达到上限时对后续请求施加背压。取消、无输出、发送失败及停用/重载均需释放或排空票据，不能让一个故障永久阻塞队列。

例如，A 先生成、B 后生成：B 可以在 A 合成语音时生成，但 B 的交付要等待 A 完成。模型历史只说明内容已生成；发送接口成功只说明获得接口回执，都不等于对方已读。原生适配器内的工具发送也需受同群顺序控制；后台插件消息、管理员命令、私聊、其他平台和真正流式路径不应假定已由该机制覆盖。

TTS 使用独立串行锁，示例客户端排队最多 120 秒；网关也分别限制排队与模型加载，示例加载最多 75 秒。模型生成阶段以真实完成进度刷新 20 秒无进度期限，客户端读取留 5 秒传输余量。每个阶段的独立等待、清理和有限重试可能叠加；20 秒不是端到端总时间。合成失败保留原文，避免另一层重复触发合成。具体进度和音频质量策略见[语音系统指南](voice-system.md)。

## 验收与排错

| 场景 | 应验证的结果 |
| --- | --- |
| 原生失败、STT 未配置 | 本地回退按正确顺序触发；每段预算与错误分类可见 |
| 两条语音并发，另有视频或输出复核 | 共享 ASR 同时只处理一项；锁等待计入期限；取消后其他任务仍能继续 |
| 长音频、静音及非静音空结果 | 片段有序且无遗漏；静音策略可复核；非静音空段不冒充成功 |
| 五个不同会话同时到达 | 最多四个进入该文字提供商；第五个等待或按期限失败；取消释放许可 |
| 同群连续两轮 | 模型阶段串行；下一轮可与上一轮交付重叠；最终发送顺序受控 |
| 队列满、TTS 超时、发送失败或重载 | 背压生效；文字回退和通知符合策略；票据、锁、子进程和临时文件释放 |
| 引用语音、多个语音附件、不同群与私聊 | 转写与消息来源对应，不跨用户或会话混用；逐一检查实际支持的路径 |

先用模拟控制时钟和失败注入，再检查安装版及运行实例；最后按授权使用真实消息与接收端验证。记录各阶段排队、处理、错误类别和脱敏标识，不记录私密聊天或原始音频。上述曾有安装版回归、共享锁真实互斥和视频音轨转写验证，但不代表所有设备、长音频或真实 QQ 全链路均已通过。
