# Windows QQ Bot 部署方案

这是一份面向人类和 AI Agent 的 Windows QQ Bot 架构与复现指南。目标是搭建一个具有自定义人格的聊天助手：能在私聊和群聊中理解上下文，按需处理图片、语音与视频，并在隔离环境中完成文件和编程任务。

本仓库只提供方案描述，不包含插件源码、安装程序、配置备份、模型权重、角色资料或参考录音。实际部署需要自行安装各组件，并准备自己有权使用的账号、模型与素材。部分定制功能依赖未在此仓库发布的插件或适配，不能仅凭本说明完整复现。

**交付目标：**先完成可用的文本聊天，再逐步增加会话、工具和多模态能力。每一阶段都应有独立验收结果；不能把“服务正在运行”当成“全部功能已经可用”。

## 给执行 Agent 的任务说明

如果你是受委托搭建本方案的 Agent，请按以下工作方式开展：

1. 先调查目标机器的操作系统、用户权限、已安装软件、现有配置和正在运行的服务，记录版本与兼容性；不要假设本文的配置字段适用于所有版本。
2. 与用户确认目标：只需文本聊天，还是还要语音、图片、视频、联网搜索、沙箱和文件交付；按需分阶段实施。
3. 记录哪些能力由上游组件提供，哪些需要另找兼容插件或自行开发。本文不提供定制插件源码，不能把某项能力当作现成配置开关。
4. 为目标环境建立独立工作目录与配置备份。检查占用端口、依赖与账号权限，避免覆盖现有部署或把现有密钥写入仓库。
5. 按下文阶段逐项实施和验证；完成一项后再启用下一项。验证时使用用户授权的测试账号和测试材料，真实发消息前取得明确授权。
6. 每个阶段汇报安装版本、启用组件、验证结果、未通过或未测试的项目及可恢复的回滚方式。遇到缺失的插件、权限或服务时明确说明，不能伪造成功。

可将下面的文字作为复现任务起点，根据实际需求补充，不要把占位内容当作真实配置：

> 请参考这份部署指南，在我的机器上搭建一个带自定义人格的 QQ Bot。先检查现有环境与可用组件，向我说明文本聊天、多模态、语音和工具沙箱分别需要什么；优先完成文本链路，再逐项实施可选能力。涉及账号登录、密钥、第三方素材或真实消息时由我提供授权。请验证用户和工作区隔离，记录版本、限制与回滚步骤，不要公开我的个人数据。

## 架构

```text
QQ 用户
  │
  ▼
QQ 客户端 + SnowLuma（消息接入）
  │ OneBot 反向 WebSocket
  ▼
AstrBot Desktop（会话、插件、模型路由）
  ├── 本机 Codex CLI 桥接 → 模型服务
  ├── WSL + Docker + Shipyard Neo → 用户隔离的工作区与工具
  ├── 可选的图片、视频和语音输入处理
  └── 可选的 GPT-SoVITS 语音服务 → 语音回复
```

以上是组件分工示意。具体可用功能取决于安装的插件、版本与平台支持；第三方服务的接口和可用性可能变化。

## 请求处理流程

1. **接收事件**：消息平台传入私聊或群聊事件，解析当前发送者、会话和消息类型。
2. **准入与唤醒**：先判断事件是否指向机器人，再检查命令权限、群聊唤醒、续聊窗口和频率限制；不符合条件则忽略。
3. **准备上下文**：区分当前消息、明确引用、历史对话和可用的群聊背景。图片或音频只在对应作用域中读取，并受大小、数量、时长和有效期限制。
4. **模型生成**：以当前用户发言为主，加入经过预算控制的历史和必要的角色指令。外部资料、群消息和附件内容均视为不可信输入，不能覆盖系统权限。
5. **工具执行**：仅在工具已启用且当前发送者身份可验证时，将允许的调用路由到该用户的隔离工作区；未经授权不读取或发送其他用户的文件。
6. **结果交付**：需要时先完成文件生成、媒体转换或语音合成，再通过原消息平台返回；发送接口回执只能确认接口返回的状态，不能将模型生成或接口成功等同于接收端实际收到。
7. **记录与清理**：记录必要的阶段耗时和错误类型，清理临时文件并执行资源回收。失败、取消或超时后释放锁、队列和子进程。

## 部署顺序

### 1. 准备主机和消息接入

1. 在 Windows 上安装 QQ 客户端、SnowLuma 和 AstrBot Desktop，分别按各项目的安装说明启动。
2. 通过 SnowLuma 完成 QQ 登录，并确认消息接入组件处于可用状态。
3. 在 AstrBot 中配置对应的 OneBot 平台接入。采用反向 WebSocket 时，在 AstrBot 配置监听端，在 SnowLuma 配置连接端；两端的地址、端口和访问令牌必须一致。
4. 单机部署优先使用回环地址 `127.0.0.1`。自行生成高强度令牌，不使用示例值；若确实需要跨机器连接，应先设计认证、加密和网络访问控制。
5. 确认连接建立，再使用测试账号发送一条普通消息，检查接收和回复是否正常。

菜单名称和字段以所安装版本为准。消息平台可能限制自动化行为；部署者应自行核对适用的服务条款与账号风险。

#### AstrBot 与 SnowLuma 的具体连接示例

下面是一组单机参考值，可直接帮助 Agent 对照界面逐项配置。端口仅为示例：如果已被占用，应选择新的空闲端口，并同步修改两端。

| 项目 | AstrBot：OneBot v11 服务端 | SnowLuma：OneBot WebSocket 客户端 |
| --- | --- | --- |
| 作用 | 监听反向连接 | 主动连接 AstrBot |
| 本机地址 | `127.0.0.1` | `ws://127.0.0.1:18765/ws` |
| 端口 | `18765` | URL 中同样使用 `18765` |
| 类型 | `aiocqhttp` / OneBot v11 | `wsClients`，角色 `Universal` |
| 访问令牌 | 部署者生成的随机值 | 填入同一个随机值 |
| 状态 | 启用平台 | 启用该 WebSocket 客户端 |

AstrBot 上游的接入步骤见 [OneBot v11 文档](https://docs.astrbot.app/platform/aiocqhttp.html)。SnowLuma 实际字段和角色合法值可对照其 [OneBot 配置定义](https://github.com/SnowLuma/SnowLuma/blob/main/packages/onebot/src/config.ts)。具体界面命名可能随版本变化。WebUI 管理密码、OneBot 连接令牌与 QQ 登录状态是不同的凭据，不要混用。

这两个片段只表示**局部字段的对应关系**，不是完整配置文件，也不是可直接覆盖已有配置的文件：

```json
{
  "type": "aiocqhttp",
  "enable": true,
  "ws_reverse_host": "127.0.0.1",
  "ws_reverse_port": 18765,
  "ws_reverse_token": "<由部署者生成并妥善保管的随机令牌>"
}
```

```json
{
  "name": "astrbot-local",
  "enabled": true,
  "role": "Universal",
  "url": "ws://127.0.0.1:18765/ws",
  "accessToken": "<与 AstrBot 相同的随机令牌>"
}
```

在 SnowLuma 中，该客户端属于 `networks.wsClients`。优先使用 WebUI 添加；配置可能按 QQ 登录账号分别保存，因此切换账号后要核实该账号实际使用的 OneBot 配置。不要公开、截图或提交填入真实令牌后的配置。先启动 AstrBot 的监听，再启动 SnowLuma 连接，检查“在线”和“已连接”；最后用经授权的测试消息确认实际收发。连接成功与收到回复是两个验收结果。

PowerShell 可只检查监听状态；这里不读取或展示任何配置和令牌：

```powershell
Get-NetTCPConnection -State Listen -LocalPort 18765 -ErrorAction SilentlyContinue |
  Select-Object LocalAddress, LocalPort, State
```

如果没有监听，先检查 AstrBot 平台是否已启用；若正在监听但未连接，再核对 SnowLuma 客户端是否启用、URL、路径和令牌。两端的连接端口和令牌必须对应；不应关闭认证来掩盖配置错误。

### 2. 配置模型

1. 安装并登录 Codex CLI；认证由部署者在自己的主机完成，不向仓库提供登录状态。
2. 在 AstrBot 中接入与当前版本兼容的本机 CLI 桥接适配，选择部署者实际可用的模型及参数。
3. 先用纯文本验证，再依次测试图片输入、图片生成和工具调用。模型能力、访问资格及限额以实际账号与服务支持为准。
4. 按聊天场景设置会话隔离和上下文长度。群内共享对话与工具工作区的用户隔离是不同层次，需要分别验证。

本方案使用的桥接包含本地定制，源码未随本文发布。读者需要自行获得兼容的桥接实现；不同实现不一定具有相同功能或安全边界。

#### AstrBot 模型提供商的参考配置

桥接可调用部署者本机已登录的 Codex CLI；其工作路径与可执行文件必须由部署者在本机填写。以下是**自行开发桥接时的设计示意**，其中类型、ID 和字段名是虚构示例，并非 AstrBot 内置配置，也不保证适用于任何现有插件：

```json
{
  "id": "example-local-provider",
  "type": "example_codex_provider",
  "enable": true,
  "provider_type": "chat_completion",
  "model": "default",
  "modalities": ["text", "image"],
  "timeout": 90,
  "codex_executable": "<本机 codex 可执行文件的绝对路径>",
  "workspace": "<仅供桥接使用的本机工作目录>",
  "model_reasoning_effort": "<可选；由模型及当前版本支持的值决定>",
  "enable_sandbox_tools": false,
  "sandbox_reuse_scope": "session"
}
```

1. 先安装或开发兼容桥接，并在 AstrBot 中确认它注册的实际提供商类型；上面的虚构类型不应直接填入真实配置。没有桥接时，不能只填入 JSON 就获得功能。
2. 使用部署者自己的登录状态，确认运行 AstrBot 的系统用户可执行 Codex CLI。不要把 CLI 登录文件复制到公开仓库或沙箱。
3. `model=default` 只表示由当前安装和配置决定模型；也可以在确认账号权限与当前文档后指定可用模型。模型名和推理强度不要按历史截图盲填。
4. 若实际桥接支持对应字段，可先只启用文本/图片并设置例如 90 秒总期限，在 AstrBot 的模型管理界面完成一次非敏感文本测试。总期限是否包括排队和媒体处理，应以具体实现验证。
5. 外部沙箱通过测试后，才在实际桥接中开启对应的沙箱工具开关，并将 AstrBot 的 `computer_use_runtime` 设为 `sandbox`。桥接应在两项条件同时满足时才声明工具能力；具体字段以插件实现为准。
6. AstrBot 不同版本可能分别保存提供商来源和模型条目；在 UI 中选好已注册的提供商和模型，确认实际被聊天会话选中，不要复制整份旧版主配置。

桥接还需限制宿主环境工具和插件，确保来自聊天的工具请求只进入经验证的外部沙箱。若采用其他桥接，其字段、认证方式、并发与安全实现都可能不同。

如果需要同一个群的成员共享聊天上下文，可在确认对应版本支持后评估 AstrBot 的 `platform_settings.unique_session` 设置，例如 `false`。此值会影响会话组织，设置后应实际测试同群共享、不同群隔离与私聊隔离。**共享会话不等于共享沙箱**：工具执行仍需基于本轮真实发送者划分工作区；若现有版本或插件做不到这一点，不应在共享会话中开放文件和执行工具。

### 3. 可选：配置工具沙箱

1. 安装 WSL、Linux 发行版和 Docker，按 Shipyard Neo 的文档部署控制服务与执行环境。
2. 为控制服务配置认证，限制监听地址与网络访问范围；不要把 Docker 控制接口暴露到公共网络。
3. 在 AstrBot 中配置沙箱连接，并按机器资源设置 CPU、内存、工作区配额及空闲回收策略。
4. 将工作区映射到可核验的真实用户身份；身份不明确时拒绝执行。分别验证不同用户不能访问彼此的文件，并检查群聊和私聊的归属规则。
5. 验证重启后的工作区、配额、回收和文件交付行为，再按需开放工具。

容器、WSL 和应用配置共同决定隔离强度；容器并不自动保证绝对安全。Docker 控制服务具有高权限，应按自身威胁模型评估，避免挂载不必要的宿主文件或凭据。

#### AstrBot 与 Shipyard Neo 的具体配置

在 AstrBot 的“配置文件 → AI 配置 → 能力 → 使用电脑能力”中，参考[官方沙箱说明](https://docs.astrbot.app/use/computer.html)配置：

| 配置项 | 单机参考值或策略 |
| --- | --- |
| Computer Use Runtime | `sandbox` |
| 沙箱驱动器 | `Shipyard Neo` |
| Shipyard Neo API Endpoint | `http://127.0.0.1:18114`，以实际 Bay 监听地址为准 |
| Access Token | 部署时为 Bay 单独生成；只在受保护的本地配置中填写 |
| Profile | `python-default`，并核对已启用的 `filesystem`、`shell`、`python` 能力 |
| 每个执行环境 | 可从 2 CPU、2 GiB 内存和空闲 1200 秒回收开始，按实际资源调整 |
| 工作区数据 | 分别设置用户总额、系统总额、保留与回收策略；不要把停止容器等同删除数据 |

以上是参考部署，并非上游默认配置。WSL 中的 Bay 要能从 Windows 本机访问，且 Docker/容器端口发布仍需受限；用回环 URL 填写 AstrBot 配置本身不能证明其他网络接口没有暴露。浏览器能力与任意宿主目录挂载不默认开启。

### 4. 可选：配置语音和媒体

1. 根据上游文档准备 GPT-SoVITS 运行环境，以及有权使用的模型权重和参考录音。
2. 部署与 AstrBot 兼容的语音服务和适配，保持服务访问范围受限，并设置超时、资源释放和合成失败后的文字回退。
3. 按需接入语音转写、图片理解或视频理解。对使用外部服务处理的媒体，应告知使用者相应的数据流向。
4. 用自行准备的测试文本和媒体确认格式、时长、资源占用与回复质量。不同硬件和模型的效果可能不同。

语音适配、参考素材和模型权重未在此发布。第三方素材、插件与模型须分别核对许可和使用范围。

#### GPT-SoVITS 语音模型方案：结构与选型

GPT-SoVITS 通常由 GPT 文本到语义模型和 SoVITS 声学模型协同工作。不同版本及分支的声学结构、接口和权重格式可能不同；选择两个检查点时，应以同一版本官方说明、基础模型和训练记录为准。相同轮数或采样参数不保证产生相同音色。

```text
模型回复 → 语音适配（检查用户偏好和文本）
         → 本机 TTS 服务（排队、期限、健康状态）
         → GPT 语义生成 → SoVITS 声学生成 → 音频质量检查
         → AstrBot 语音消息 → QQ
                                 └─ 失败或不满足条件：返回原始文字
```

下表说明如何选择参数，**不是某个真实部署的数值快照**；不同版本字段可能不同，务必按实际模型和上游文档验证。

| 配置项 | 如何选择与验证 |
| --- | --- |
| GPT、SoVITS 权重 | 选择相互兼容、来源清楚且有使用授权的一组；私下记录版本、来源、哈希 |
| 参考音频和文本 | 根据版本要求准备经授权的短音频及逐字文本；二者不匹配时优先修正数据 |
| temperature、top-k、top-p | 按上游建议起步；对同一段测试文本逐项调整并比较音色、发音和稳定性 |
| repetition penalty、CFM 步数与 CFG | 仅当模型版本及接口支持时设置；增加步数可能影响时延，效果需实测 |
| 随机种子 | 调试时固定种子对照，正式部署可按需要随机化；避免公开可与私有日志关联的种子和回执 |
| 文本与语义长度 | 设置应用侧可配置上限；超限保留完整文字或明确提示，不冒充模型通用上限 |
| 分句 | 根据模型和时延需求选择；若要整段合成，先验证对应版本的不切分选项 |
| 单次期限与队列 | 分开设定排队、合成和总时限；受限制的重试失败后回退文字 |
| 资源释放 | 根据显存和响应需求设置空闲卸载；忙碌请求或活动租约期间不卸载 |

输入副本可对 emoji、颜文字和符号做可控清理，并将常见四则运算符转成可朗读文字；原聊天文本保持不变。对英文和多语言输入，应根据模型的语言能力分别验证。长静音、持续弱信号或超时都应触发明确失败处理；PCM 有声音并不证明逐字准确或主观听感合格。

#### 一个可核对的上游 TTS 接口示例

以安装目录根下运行的上游 [GPT-SoVITS `api_v2.py`](https://github.com/RVC-Boss/GPT-SoVITS/blob/main/api_v2.py) 为例。**仅在核验所安装版本支持这些参数、已完成依赖和权重配置后**，可使用另选的本机端口启动：

```powershell
python api_v2.py -a 127.0.0.1 -p 19080 -c GPT_SoVITS/configs/tts_infer.yaml
```

下面是 `/tts` 的 POST 请求体结构示意。参考音频路径是服务所在机器上的路径；部署者需替换占位符，并让参考文本与音频逐字一致。不得复制用户的真实音频路径或原文到公开仓库。实际必填项和可用参数以安装版本为准：

```json
{
  "text": "你好，很高兴见到你。",
  "text_lang": "zh",
  "ref_audio_path": "<服务主机上的授权参考音频路径>",
  "prompt_text": "<参考音频对应的逐字文本>",
  "prompt_lang": "zh",
  "text_split_method": "cut0",
  "batch_size": 1,
  "media_type": "wav",
  "streaming_mode": false,
  "seed": -1
}
```

上游当前的 `cut0` 表示不按此方法分段，实际版本及下游是否另行拆分仍需验证；其他参数应在确认版本支持后再填写。返回音频后，先检查 HTTP 状态、类型、音频可解码性和实际时长，再进行听验；具体音频采样率由模型输出决定。

测试时，先把上面的结构保存为**本机私有文件**并替换占位符，再向本机服务发送请求。以下命令中的两处路径是占位符，必须自行替换；音频与请求体不应提交到仓库：

```powershell
curl.exe --fail -X POST 'http://127.0.0.1:19080/tts' -H 'Content-Type: application/json' --data-binary '@<本机请求体文件>' --output '<本机临时音频文件>'
```

返回失败时检查服务日志与 HTTP 错误，但不要复制包含用户文本或绝对路径的原始日志。返回成功后应自行播放并检验，不能仅凭文件存在断定合成质量。

`api_v2.py` 同时提供模型切换和进程控制接口，不应直接暴露在公网或让聊天用户决定本机权重、参考音频路径。单机部署只监听回环地址；若跨机使用，需在独立受控网关实现认证、传输加密、请求限制及接口白名单。不要假定上游自带所需的认证、空闲卸载、重试或用户隔离。

#### 从零搭建可替换的语音链路

1. **确定声线权利与模型**：使用有权使用的数据和声线。准备与实际 GPT-SoVITS 版本匹配的 GPT 权重、SoVITS/CFM 权重和必要依赖；本仓库不提供原权重，也不提供训练数据或声线。
2. **先单独验证推理**：按 [GPT-SoVITS 官方项目](https://github.com/RVC-Boss/GPT-SoVITS)的对应版本安装依赖，确认 GPU、模型加载和音频输出。根据选用版本，按上游支持的参考音频和文本方式开始，确认请求与模型版本匹配。
3. **锁定版本和身份**：在私有部署记录中保存上游版本、推理 runtime 版本、两个权重的来源和哈希；不要公开权重路径、音频素材或训练数据。
4. **部署本机网关**：提供受限的本机接口，设计健康检查、串行队列、单次期限、失败处理、按需加载和空闲卸载。上表的网关行为属于定制实现，不能假定标准上游 API 自带。
5. **连接 AstrBot TTS**：使用与 AstrBot 版本和语音服务兼容的 TTS 提供商适配。在 AstrBot 中启用并选择实际安装的 TTS 提供商；适配器的类型和 ID 由所选插件决定，本仓库不提供插件源码。
6. **设置回复策略**：先小范围测试短句、长句及含数字的完整句子、符号规范化、超时和文字回退，再根据硬件决定语音触发概率、用户偏好与排队策略。
7. **分别验收**：确认服务健康、实际生成有效音频、文字内容完整、主观音色合格，以及经授权的测试接收端能播放；将每一项单独记录。仅健康检查成功不能证明真实合成或 QQ 发送成功。

如果语音网关实现了只读 `/health` 端点，可在本机查看状态；确认该端点不会触发模型加载或合成后再用于监控。模型暂时未加载而网关正常时，可能只是按需卸载，不应反复重启。上游服务没有该端点时，应使用其自身支持的健康检查方式。

#### AstrBot 的 TTS 配置与适配契约

在支持相应字段的 AstrBot 版本中，[配置参考](https://docs.astrbot.app/dev/astrbot-config.html)列出了 `provider_tts_settings`。以下仅为**局部示例**；`provider_id` 必须替换成实际安装并启用的 TTS 提供商 ID，不能创建一个不存在的提供商：

```json
{
  "provider_tts_settings": {
    "enable": true,
    "provider_id": "<已安装的 TTS 提供商 ID>",
    "dual_output": false,
    "use_file_service": false
  }
}
```

优先通过 WebUI 选择 TTS 提供商并保存对应配置文件；再检查会话级规则是否启用 TTS。`dual_output` 控制是否同时输出文本和语音；启用文件服务会增加音频经 HTTP 链接提供给消息平台的数据流，需要另行评估访问控制。版本差异和实际路由以所用版本文档与测试结果为准。

如果没有兼容插件，需要自行实现连接层。最小契约应覆盖：读取经验证的当前会话设置；接收要朗读的文本；将请求发送到固定的受控 TTS 地址；限制等待时间和音频大小；检查响应状态、内容类型和音频格式；将临时音频作为框架支持的语音结果返回；在失败或取消时清理临时文件并回退文字。用户消息不得指定 TTS 的服务地址、服务端本地路径或模型权重。模拟测试先覆盖空文本、超时、格式错误和取消，再按用户授权进行实际合成与接收端验收。

#### 自行训练或准备类似声线

如果部署者没有可用的授权权重，执行 Agent 可以依照所选 GPT-SoVITS 版本的官方流程设计训练：

1. 取得语音及其文字使用授权；整理音频、逐句文本和说话人标签，去除损坏片段、重叠人声与明显错误的转写。训练和验证材料应由部署者私下保管。
2. 按当前上游版本的要求完成切分、重采样、音频/文本对齐、特征提取和标注检查。不要假设不同 V5 分支或已有模型使用相同预处理参数。
3. 将训练集和验证集分开，避免同一音频片段同时进入两边。为比较效果准备未参与训练的短句、长句、数字和标点测试样例。
4. 使用与目标 runtime 对应的 GPT 与 SoVITS/CFM 训练流程，记录各阶段版本、基础模型、配置、轮数和检查点来源。训练轮数仅是定位检查点的标识，模型质量仍需验证。
5. 对候选检查点分别听辨音色、自然度、读音、尾句完整性和噪声；可辅以转写核对，但转写一致不替代听感。记录失败案例及资源开销，再选择组合。
6. 按所选模型版本确认参考音频、参考文本和推理实现的要求；不要仅凭更改配置字段假定模型支持某种模式。

对于输入语音的识别，转写模型属于另一条 ASR 链路，与上述输出语音的 GPT 和 CFM 权重无关；按“平台转写 → 已配置 STT → 可选本地离线转写”的顺序分别测试即可。

## 给实施者的分阶段交付

| 阶段 | 要做什么 | 验收标准 | 未通过时 |
| --- | --- | --- | --- |
| A. 本机消息链路 | 配置 QQ、SnowLuma 和 AstrBot 的 OneBot 连接 | 发送一条经授权的测试消息，确认接收与回复 | 分别检查登录状态、监听和两端连接配置 |
| B. 模型与人格 | 配置一个可用提供商，建立简短角色指令 | 多轮文本能回答，重置后旧上下文不再混入 | 先在 AstrBot 独立测试提供商，再查路由和超时 |
| C. 群聊行为 | 增加唤醒、引用、续聊、限频 | 多用户交错发言时，能区分触发人、其他人和机器人本身 | 先检查事件解析与会话键，不降低权限绕过 |
| D. 外部工具 | 建立沙箱、工具白名单和身份映射 | 两个测试用户的文件不能相互读取；缺少身份时拒绝执行 | 暂停工具，对照归属和沙箱配置排查 |
| E. 媒体 | 按需启用图片、输入语音及视频 | 当前消息、引用消息和失败回退分别通过测试 | 优先回退文字，明确未处理的媒体 |
| F. 输出与运维 | 添加语音输出、文件交付和监控 | 发送结果有回执；失败、重启和回滚可解释 | 保持文本服务可用，不宣称未确认的交付成功 |

应在各阶段记录组件版本、配置项名称、验证方法和结果。上游接口可能升级，应以实际版本的官方说明和程序行为为准。

## 角色与提示词设计

角色可由部署者自行定义，建议把内容分成四层：

1. **行为边界**：区分系统权限、平台规则、工具权限与不可信消息；用户引用的文本或群消息不能提升权限。
2. **基础人格**：用短段落描述名字、表达风格和互动原则，优先让角色自然回应，不要求每句话都套固定句式。
3. **按需资料**：将背景、世界观、关系和场景拆成独立资料，按当前话题加载，避免每轮重复塞入全部内容。
4. **当前任务**：保留当前发送者的问题、明确引用及相关图片；将群聊背景标记为背景，避免把其他人的经历当成当前用户的经历。

可自行编写例如以下简短人格示例，替换为有权使用的角色设定：

> 你是一位温暖、活泼而有边界感的聊天助手。优先回应用户眼前的问题；不确定时坦诚说明。涉及工具、文件或他人信息时，遵守当前请求和系统赋予的权限。语音或图片不可用时，不要假装已经听到或看到。

角色资料不应包含真实个人联系方式、私密聊天记录或未获授权的原作内容。角色风格属于可替换配置，不应与账户凭据或系统安全规则写在一起。

## 会话、并发和群聊

- **会话键**：至少区分平台、机器人实例、聊天类型及聊天对象。私聊与不同群组互不混用；是否同群共享聊天历史由部署者明确选择。
- **用户身份**：聊天历史可以按群共享，但文件和工具权限应按当前真实发送者划分。会话 ID 不能单独作为用户授权依据。
- **群消息来源**：优先识别本轮消息、直接引用及明确提及，再按预算补充群聊背景。保留引用关系，避免时间相邻的两个话题互相混淆。
- **唤醒与续聊**：可组合使用 @、引用机器人、唤醒词和有限时续聊；对机器人自己的事件、指向他人的消息和管理命令设置独立处理规则。
- **限频与错误**：为用户和群分别设置窗口及上限，避免连续触发和机器人循环。主动请求失败时可给出简短提示；自动插话失败可选择静默并保留诊断。
- **并发与顺序**：为模型请求、同会话访问及语音合成设定独立队列与期限。允许重叠处理时，要单独设计群内发送顺序、取消清理与背压。
- **会话复用**：如果桥接支持持久会话，应为不同群、私聊和模型选择明确的隔离键；清空历史、会话丢失、模型变更或进程重启后的恢复行为需要测试。不能因连接中断而盲目重复提交已执行的工具调用。

### 事件与上下文的抽象结构

实现适配时，可以把平台事件整理成如下**概念结构**；字段仅解释需要保留的信息，并非任何上游 API 的实际参数：

```text
当前事件
├─ 来源：平台、机器人实例、聊天类型、聊天对象
├─ 发言：当前发送者、消息标识、时间、文本和附件
├─ 关系：是否提及机器人、明确引用的消息及其发送者
└─ 状态：是否唤醒、是否续聊、已执行工具和发送结果

模型输入
├─ 可信指令：行为边界、工具规则和部署者配置的人格
├─ 当前消息：本轮文本、明确引用与可用的当前媒体
├─ 对话历史：按会话隔离并受长度预算约束
└─ 临时背景：相关群消息或检索结果，标记为不可信资料
```

会话键可以概念性地由“平台 + 机器人实例 + 聊天类型 + 聊天对象 + 对话版本”组成；用户工作区键另加“真实发送者”。需要跨群复用时应明确设计其作用域，不能仅因群会话共享就共享文件。上述键中的实际标识属于私有数据，日志不应直接输出。

如果选择 Codex 集成，可参阅 [Codex CLI 官方说明](https://learn.chatgpt.com/docs/codex/cli)、[非交互模式](https://learn.chatgpt.com/docs/non-interactive-mode)以及 [Codex 集成方式说明](https://developers.openai.com/blog/codex-as-a-platform)。这些接口本身不等于 AstrBot 的现成提供商；桥接需自行处理消息转换、上下文、超时、错误和隔离。

## 工具和文件：实现契约

希望其他 Agent 实现接近本方案的能力时，可按以下约束设计，而不是直接把宿主机工具开放给聊天模型：

1. **工具声明**：明确列出允许的文件、代码执行和媒体工具及其参数；校验参数类型、大小、路径和超时。
2. **身份绑定**：由可信的平台事件获取当前平台、聊天与发送者；缺少身份、事件不匹配或已经过期时拒绝执行。
3. **工作区归属**：为每个真实用户映射独立的工作区；跨群复用同一用户的工作区属于可选策略，需要事先告知并验证。
4. **执行边界**：将代码和工具调用发送到受限制的外部环境，限制 CPU、内存、执行时间、文件大小、网络和挂载；不要向工具容器提供宿主登录凭据。
5. **文件路径**：默认只接受工作区内的相对路径，规范化路径后确认仍处于工作区；拒绝路径穿越、任意宿主路径和跨用户访问。
6. **私发授权**：如要把群内结果发到私聊，只允许发给当前经验证的请求者，并以明确请求作为授权；不要接受模型自由指定的第三方收件人。
7. **交付回执**：生成文件、上传和发送是不同阶段。任一阶段失败时应报告失败或状态未知；不要仅凭生成成功宣称已送达。
8. **资源生命周期**：区分容器运行状态和工作区数据。设置配额、空闲释放与过期策略；归档、恢复、删除和备份的影响要向用户解释。

### 建议验证的隔离案例

| 场景 | 预期结果 |
| --- | --- |
| 用户 A 在群中创建文件，用户 B 请求读取 | B 无法读取 A 的文件 |
| A 在不同群或私聊继续使用工作区 | 按部署者选择的复用策略处理，不影响 B |
| 无法取得当前真实发送者 | 拒绝执行或发送，不能用群号代替用户身份 |
| 请求访问工作区外路径或其他人的文件 | 拒绝访问，不将文件内容返回给模型 |
| 发送接口超时或没有明确回执 | 标记交付失败或未知，不声称成功 |
| 容器回收或服务重启 | 工作区是否保留、归档或过期应符合已配置策略 |

## 图片、视频、语音和表情

### 图片与视频输入

- 当前消息和明确引用的媒体优先；可以设计短期缓存支持“先发图，后提问”，但必须限制来源、容量和生命周期。
- 图片理解要求模型或适配支持图像输入。模型无法辨认时应说明不确定；使用反向搜图属于额外外部数据流，需确认隐私和可用性。
- 视频可先检查大小与时长，再由本地工具抽取带时间信息的代表性画面，并按需转写音轨。抽帧只是离散样本，不能保证覆盖完整视频。
- 媒体下载应限制来源、大小、重定向和处理时间；取消或失败时清理临时文件。外部网页、字幕和转写均属于不可信内容。

### 语音输入和输出

- 输入语音可按“平台原生转写 → 已配置的转写服务 → 可选本地模型”的顺序设计回退；每层均应有期限。无转写结果时明确告知，不能猜测语音内容。
- 对引用语音保留其来源关系；处理直接语音时不要意外丢失唤醒词。
- 输出语音需要文本策略、TTS 服务、模型与可用的参考音频。可按需要设置文本长度、队列上限、合成超时、质量检查和空闲资源释放。
- 对不适合朗读的符号可仅在合成副本中规范化；原聊天文字保持不变。合成失败或超时后应能回退文字。
- 允许用户控制语音与文字偏好时，状态应限定在当前真实用户的作用域内，不让其他人的消息改变其设置。

### 表情和视觉风格

表情包可作为独立可选功能：部署者自行提供有权使用的素材，按语境和用户要求控制发送频率，并限制单次发送数量。表情包、人物形象和语音素材的权利应分别确认，不能假设某个开源插件的许可证覆盖其加载的全部素材。

## 配置清单与示例策略

以下是需要做出的配置决策，**不是可直接导入的配置文件**。端口、时长、并发和配额由部署者结合版本与硬件自行选择，并在本机私有配置中保存。

| 项目 | 需要决定的内容 |
| --- | --- |
| 消息连接 | 本机监听地址、端口、反向连接地址及两端一致的随机令牌 |
| 模型 | 提供商、实际可用模型、并发、请求期限、上下文预算和失败处理 |
| 群聊 | 会话隔离方式、唤醒方式、续聊窗口、用户与群的限频策略 |
| 工具 | 是否启用、允许的工具、真实用户身份映射及收件授权 |
| 沙箱 | 控制服务认证、CPU/内存、存储配额、网络、工作区复用与回收期限 |
| 媒体 | 允许的格式、单次数量、尺寸/时长、缓存期限、外部服务数据流向 |
| 语音 | 是否启用、模型与参考素材、最大并发、文本限制、超时和失败回退 |
| 运维 | 健康检查、日志保留、备份恢复、升级前快照及回滚范围 |

例如，可先采用“只对明确唤醒回复、单会话串行、每人独立工作区、语音可关闭”的保守策略；所有数值和权限都应通过实际测试后再调整。

### 参考起步参数

以下数值用于帮助实施者进行初次容量规划，**不是上游组件默认值，也不是性能保证**。不同环境应先从更严格的限制开始，再根据验证结果调整。

| 项目 | 可用于试运行的参考值 | 需要同时检查 |
| --- | --- | --- |
| 模型总期限 | 例如 90 秒 | 排队、媒体处理、模型生成与工具续轮是否共用期限 |
| 模型并发 | 例如最多 2 个不同会话的请求 | 同一会话仍需串行或其他明确的一致性保护 |
| 群聊续聊 | 例如明确唤醒后 45 秒内允许一次续聊 | 发送者、群、机器人实例与重复事件是否隔离 |
| 沙箱资源 | 例如每个执行环境最多 2 CPU、2 GiB 内存 | 同时运行多个环境时主机可用资源是否足够 |
| 空闲计算释放 | 例如运行环境闲置约 20 分钟 | 释放计算环境与删除用户文件必须分开 |
| 用户数据额度 | 例如每用户约 512 MiB | 总容量、单文件大小、归档和备份空间另行限制 |
| 视频理解 | 例如单个视频最多约 90 秒，抽取最多 6 帧 | 媒体大小、总处理期限及模型图片输入预算 |

这些是独立设计的示例值，并非某一实际部署的配置；实现仍须检查实际产品和机器是否支持。

## 功能设计参考

- **群聊与私聊**：按实际消息来源区分会话；群聊可共享对话背景，同时单独限制用户工具与文件的访问范围。
- **唤醒和频率控制**：根据实际平台事件设置唤醒、续聊和限频规则，避免机器人互相触发或重复回复。
- **图片和视频**：优先处理当前消息及明确引用的媒体；限制数量、大小与缓存时间，并区分当前内容和历史背景。
- **语音**：语音合成失败时保留文字回复；按资源条件限制队列、超时和输入长度。
- **文件交付**：只从已授权的用户工作区读取文件，限制大小，并根据实际发送回执判断是否交付成功。
- **可观测性**：优先记录耗时、阶段和错误类型；避免在日志中记录聊天正文、媒体内容和凭据。

上述是设计思路，具体行为依赖所使用的适配和配置，不代表上游组件默认提供全部功能。

## 安全与隐私

- 不要上传访问令牌、API 密钥、密码、登录会话、Cookie 或包含它们的配置文件。
- 不要上传聊天记录、QQ 号、群号、数据库、日志、浏览器配置、个人路径、内网地址、截图或原始媒体。
- 使用独立测试账号与测试资料；对需要上传至外部服务的内容，先确认使用者知情。
- 升级 AstrBot、桥接、消息接入或沙箱后，重新验证连接、身份隔离、工具权限及文件交付。
- 如果凭据意外进入公开历史，应立即撤销或轮换，并检查受影响服务；仅删除当前文件并不能移除历史。
- 公开前审查当前文件**与所有拟公开的提交历史、分支和标签**，以及仓库简介、Issue、PR、Release、Actions 日志和附件。新建干净历史可减少旧提交带出的关联信息；不要未经备份及授权强制改写现有协作仓库。
- 公共仓库的所有者和仓库 URL 通常会展示 GitHub 账号名。若不希望账号与项目关联，应先由所有者选择合适的发布账号，内容脱敏无法隐藏仓库所有者。

## 排错思路

| 现象 | 先检查 | 恢复与验证 |
| --- | --- | --- |
| QQ 已登录，但 Bot 收不到消息 | 消息接入是否在线、OneBot 反向连接状态、地址端口和两端令牌是否一致 | 先验证连接，再用授权的测试消息确认事件到达 |
| AstrBot 能收到消息，但没有回复 | 平台是否启用、唤醒规则、权限、会话路由、模型提供商和日志中的错误类型 | 先在框架自带测试界面验证模型，再检查群聊触发条件 |
| 多轮对话串到其他人或其他群 | 会话隔离配置、会话键和明确引用的归属 | 使用两个用户和两个会话交错测试；隔离未通过前暂停共享历史 |
| 图片看不到或内容不对 | 媒体下载、当前消息与引用关系、模型图片输入支持、数量和大小限制 | 用自行准备的简单图片分别测试直发、引用和后续提问 |
| 语音没有被理解 | 平台转写、备用转写是否启用、格式与时长限制、队列及超时 | 各层单独验证；失败时向用户说明没有取得内容 |
| 有文字但没有语音 | TTS 提供商、服务健康、输入策略、队列、模型文件和超时 | 先单独测试合成，再测试消息平台的语音发送；保留文字回退 |
| 工具不可用或工作区满额 | 沙箱认证、服务健康、用户身份、资源与工作区配额 | 先确认数据保留策略，不要未经确认删除用户工作区 |
| 文件已生成但没有收到 | 文件是否在当前用户工作区、大小限制、消息平台传输和发送回执 | 分别验证生成、上传、发送三个阶段，避免重复发送 |
| 重启后行为变化 | 组件版本、插件启用状态、持久化配置、登录和依赖状态 | 对照升级前记录逐项恢复，重新执行隔离及消息测试 |

排错时优先查看脱敏后的错误类型、阶段和时间；不要把完整日志、聊天内容、认证配置或个人截图粘贴到公开问题中。健康接口成功只表明对应服务可访问，不代表真实消息、模型和媒体链路均已验证。

## 部署交接记录模板

建议执行 Agent 在部署者的私有位置保存以下记录；分享或提交之前需另行脱敏：

```text
目标与范围：文本 / 群聊 / 图片 / 视频 / 输入语音 / 输出语音 / 沙箱 / 文件交付
部署时间与环境：操作系统、架构、硬件资源（按需）
组件清单：组件名称、版本、来源、安装位置（私有记录）
依赖关系：消息接入 → 框架 → 模型；可选沙箱、转写和 TTS
非秘密配置：已启用功能、隔离策略、并发、超时、容量与回收策略
密钥存放方式：只记录保管位置与负责人，不记录密钥或登录状态
验证结果：每项测试的输入类型、通过/失败/未测试、证据范围
已知限制：未实现的适配、未验证的设备或平台、第三方服务依赖
恢复方案：受影响的组件、备份位置、恢复顺序与恢复后验证项目
```

记录“本地模拟通过”“实际发送接口返回成功”和“接收端实际收到”三个不同层次的证据；其中任何一项都不能自动证明其他项。不要把实际部署者的记录直接提交到公开仓库。

## 升级和维护

1. 升级前记录组件版本、已启用插件和互相依赖关系，备份必要配置与用户数据；备份应保存在受保护的位置。
2. 先核对新版本的安装要求、插件兼容性及第三方许可，再计划维护窗口。定制适配可能在自动更新时被覆盖。
3. 每次只升级可定位的一组组件，并保留可恢复的旧版本。恢复时尽量限定文件和配置范围，避免覆盖其他已发生的修改。
4. 升级后至少复测消息链路、模型调用、不同用户沙箱隔离、媒体处理与错误回退；未启用的功能标记为未测试。
5. 需要更换模型、身份或会话策略时，验证清空历史及进程重启后的行为；不要假定旧会话可以继续复用。

## 验收清单

- [ ] 消息接入连接正常，测试消息能收到预期回复。
- [ ] 模型身份、权限和所选功能符合预期；异常时不会泄露配置。
- [ ] 不同用户的工作区和文件互相隔离；无法核验身份时不执行工具。
- [ ] 图片、视频、语音与文件交付按实际启用的功能逐项测试。
- [ ] 重启、超时和服务不可用时的行为符合预期，相关日志不含敏感内容。
- [ ] 第三方组件及素材的许可已经核对，部署配置和备份不进入公开仓库。
