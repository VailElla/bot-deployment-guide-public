# 消息、媒体与运维设计补充

本页将近期实践整理为可选设计，补充[部署指南](../README.md)。这些能力依赖定制插件与适配，本仓库不提供实现、真实配置或私有数据。示例不是上游默认值；完成本地测试后，仍应按授权范围验证真实消息链路。

## 图片与视频上下文

短期缓存可以支持先发图再提问，但自动关联应限定平台、会话与真实发送者，设置短窗口和使用次数；当前消息自带图片或明确引用优先。重试同一事件不能重复附图，过期图片不能因为普通问候而被自动注入。引用链、原发送者、消息时间及媒体属于当前输入还是历史背景应分别标记；不要把发图人自动当成图片中的人物或所有者。

如需在重启后理解旧图，可将成功解析的图片和来源元数据保存在独立、受保护的归档中，按真实引用或明确指代恢复，不必改写原消息数据库。实现时限制每条数量、单图大小、处理时间、总容量和磁盘余量，定义保留、删除、重置和失败策略；归档失败应可观察，不能声称图片已经保存。群聊和私聊、不同用户与群之间分别测试隔离。历史图片是否进入模型还取决于上下文选择和图片预算，不能保证每次都被读取；动画、首帧与原始数据的处理也应分别验证。

视频同样要保留来源和时间关系。直接发送、引用与被选作群背景的视频应分别测试；抽帧及音轨转写只提供有限证据，不能宣称模型看过完整视频。限制大小、时长、下载来源、帧数和处理时间，失败时区分画面、音轨和转写的实际状态。

## 可选的局域网发送台

独立发送台可提供好友与群的搜索、多选、预览和文字、图片、上传音频或 TTS 发送。服务应验证目标和附件，限制批次大小、文件类型与容量，在发送前展示最终内容；保存最小化的批次状态和回执，确保同一批次请求幂等。发送接口明确拒绝、限频、超时或回执缺失要区分处理：结果不确定时暂停并先核对，避免盲目重发；只有确认未送达且策略允许时才能有限重试。

发送台具有代用户发消息的权限，默认应采用认证、访问控制和受限监听。某些可信局域网部署可按所有者的风险选择取消口令，但局域网限制和来源校验不是身份认证；网络中的其他设备仍可能使用发送台。不要把个人内网地址、目标列表、回执或登录信息提交到公开仓库。模拟发送、实际合成、接口回执与收件端确认应作为独立验收项。

## 失败分类与通知

健康检查只能说明服务可访问；模型超时、消息发送拒绝或通知自身失败仍可能导致用户没有收到回复。按阶段区分容量不足、模型超时、媒体处理、正文或语音交付失败与可选附加表情失败；按实际需要设置静默、冷却和聚合，不能用宽泛错误码把所有不同原因一并静默。

一种已部署的策略是容量不足静默、模型超时及正文/语音拒发进入通知队列，而特定附加表情发送失败单独静默。通知采用固定脱敏说明与事件编号，不外发消息正文；保留分类冷却及跨类间隔。冷却会合并或延后部分事件，应单独检查队列和发送 worker，避免将通知接口可访问误认为通知已送达。历史未发送记录是否补发需另行决定，不应自动重发原回复。

测试应覆盖同一平台错误码用于不同失败场景、超时、冷却、通知失败、重复事件、重载与重启。先用模拟和安装版测试分类，再检查实际运行实例加载状态；自然故障下是否真正通知仍需独立验证。发送预算按回复轮次还是实际消息条数计算也要明示，平台仍可能拒发，本策略只改善漏报，并不消除限流。

## 角色、唤醒与审核的边界

人格可使用第一人称自然叙述，但不能凭角色设定声称具有未验证的能力或编造事实。群聊唤醒、随机回复、审核、计次和管理员提醒是不同策略：若按直接 @ 才计次，应依据原始顶层事件，而不是引用、转发、纯文本昵称或转写结果中的伪 @。关键词和组合规则需用正常语境、数字误报、跨行及正反例回归；具体词库和群级设置由部署者自行决定并保存在私有配置中。
