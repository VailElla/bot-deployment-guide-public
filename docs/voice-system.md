# 语音系统：训练、推理与聊天接入

本页补充 [部署指南](../README.md)中的语音章节，供实施者设计可替换的 GPT-SoVITS 语音链路。此处描述的是可采用的工程方法，**并非上游默认功能**：网关、用户偏好、质量门和调度通常需要兼容插件或自行开发。本仓库不提供定制代码、声线、权重、训练音频或真实部署配置。使用声线及素材前应确认有权训练、合成和分发。

## 从数据到消息

```text
授权录音 → 清洗与标注 → 划分训练/留出集 → 特征预处理
         → 训练候选权重 → 固定测试集和多种子试听 → 选型
         → 独立推理服务 → AstrBot 语音适配 → 消息平台
用户本轮文字 ─→ 媒介意图与偏好 ─→ 文本规范化 ─→ 语音或原文回退
```

每一环的版本、输入和验证结果都应在私有交接记录中固定。语音输出与输入语音的识别是两条独立链路：TTS 权重不能替代转写模型。

## 训练与检查点

1. **整理素材**：逐条检查授权、说话人、录音质量及台词；文本与录音逐字对应。去除截断、严重重叠或无法确认来源的素材。按原始录音来源划分训练集和留出集，避免同一录音的切片或近重复句子同时进入两边。
2. **建立版本清单**：记录上游代码版本、Python 与依赖、基础模型、数据清单、预处理结果、训练配置、随机性和权重哈希；这些记录放在私有位置。更换数据或模型版本后使用新的实验目录，检查特征缓存与实际输入一致。
3. **先做基线和短试运行**：用所选版本支持的参考音频方式生成固定样例，再短时间训练，确认显存、样本纳入数、日志、保存与权重加载正常。训练 loss 不是音色或内容完整度的直接评分。
4. **按版本训练**：GPT 语义模型、SoVITS/CFM 声学模型各自采用所选版本明确支持的流程。对 V5 或其他版本的声学定制训练，先核实上游支持范围；自定义训练器和无参考推理属于额外工程，不能仅凭通用 WebUI 按钮宣称已经支持。参考音频是否必需，以所选权重、接口和实现为准。
5. **保留多个检查点**：训练、预训练基线和选中的候选分开保存；续训前确认所需优化器状态与版本，不把推理权重当成完整续训状态。比较时尽量固定一个模型，只更换另一个，并固定文案、参考条件及采样方案。
6. **停止与回退**：出现异常损失、不能加载、样本遗漏或质量退化时保留证据并停止试验。上线只部署经过试听和验证的一组权重，保留上一个可用版本和明确的恢复步骤。

## 推理参数与比较方法

| 变量 | 作用与检查 |
| --- | --- |
| GPT 与声学权重 | 必须与代码、基础模型和输入方式兼容；不同检查点分别记录来源和哈希 |
| temperature、top-k、top-p | 控制采样，影响多样性与稳定性；逐项改变，避免把一次较好的输出当成普遍结论 |
| 重复惩罚 | 可能改变重复和节奏，需同时检查漏字及停顿 |
| 声学步数、CFG | 仅在实现支持时设置；比较音质与耗时，不假设更多步数一定更好 |
| 随机种子 | 用固定种子建立可比较条件，再用多个种子检查稳定性；固定种子也不保证不同硬件或运行批次的文件逐字节一致 |
| 语义长度保护 | 限制异常生成；触及上限应按失败或不完整处理，不把该值当作语言或模型的通用能力上限 |
| 完整句与分句 | 先分别试听内容完整度、音色衔接及延迟；选择整段时同时检查网关和模型前端没有再次拆句 |

建议用覆盖短句、长句、数字、标点、语气、相似发音和较难尾句的固定留出文案。一次只调整一项，记录模型版本、条件、种子、耗时和音频标识；使用随机顺序盲听，分别评价内容完整、音色、音高、语速、停顿、噪声和尾音。自动转写可辅助发现漏字，但识别错误也要人工复核；波形合格或 loss 下降都不能代替听验。

多人评审时，每个评审者独立保存原始评价及数据集映射，不把未评价当成不合格，也不把同一音频因出现在多个条件下重复计票。可以为质量评级之外提供多选问题标签及备注，后续汇总先区分原始评分、补评和缺失项。评价及音频是否公开，由素材授权和隐私要求决定。

## 独立推理服务与资源管理

生产服务可与训练和试听使用**独立的 Python 环境、依赖、源码、模型文件、缓存、临时目录和配置**。复制后核对关键文件哈希、实际加载模块及动态库路径；单独的目录名或软链接不能证明运行时已隔离。更新训练环境的权重不会自动更新生产服务，应先在隔离环境测试、记录版本，再有计划地部署。

软件隔离仍会共享 GPU、显存、CPU 和磁盘：训练或多个推理进程可能互相争抢资源。采用按需加载和空闲卸载时，正在处理的请求与有效租约应阻止卸载；健康状态需区分网关可访问、模型未加载、模型就绪和正在处理，避免把正常的空闲卸载误判为故障。

并发应实测而非按进程数推断性能。比较串行与并发时，固定模型、文案、采样、预热、实际 worker 的进程优先级和 CPU 亲和性，记录资源、失败、首条完成和全部完成时间；验证真实请求有重叠，并区分客户端重叠与 GPU 实际执行。小样本只能说明该环境下的结果；隔离和并发数同时变化时不能单独归因。并发不一定更快，也可能增加首条等待。保留可恢复的单 worker 路径。

## 队列、期限和故障回退

网关可以把**排队、模型启动、合成、传输**分开计时：冷启动完成后再开始合成预算，客户端总期限应覆盖允许的各阶段与清理时间。实际数值由硬件和服务确定；更长的队列期限不保证合成成功，多次尝试也会增加总等待。设置请求总次数和总等待上限，取消后清理排队项、租约及临时文件。

区分可重试的超时、连接失败和服务繁忙与不可重试的非法输入、权重不兼容等错误；重试不应无限重新加载模型。首次合成失败时保留完整原文；如果已有可用音频，后续择优尝试失败可保留之前的结果。防止语音失败后框架的另一层自动再次触发 TTS，造成重复等待或重复消息。

建议分别记录排队、加载、推理、质量检查和发送所需时间，避免记录原始聊天正文及私有路径。发送接口返回成功只能证明接口回执，不能证明接收端已收到或播放。

## 朗读文本与音频质量

只在**语音副本**处理符号，展示文字和失败回退保留用户可见原文。按模型能力处理 emoji、颜文字、格式和控制字符；未知符号可以转停顿或拒绝，避免无声删除有实际含义的文字。四则运算、数字、外文和混合语言分别测试：无法可靠朗读时回退文字，不假装已经完整朗读。

按可配置策略检查文本长度，标明计数单位和支持语言；超限时返回完整文字或明确告知。单句整段合成可以减少分段拼接的断层，但需要检查长度、等待和失败率；不要为了绕过限制无条件拆分。

音频质量门至少检查响应格式、解码、采样率、时长、空音频、长静音和持续弱信号。可选的音高筛查可以在异常候选出现时有限次数重生成、择优保留；设定总合成次数并处理无法估计及后续失败。基频估计可能出现倍频或半频，**音高不等于音色，也不证明文字完整**；阈值必须结合自己的声线和实际试听校准，不应照搬。

可选的重复文本策略是对规范化文本保存哈希和有限时效，在首次与短期重复时选择不同种子；需要明确范围、并发预留、失败释放、过期清理和重启后的持久化。记录哈希也可能存在隐私风险，应限制保存与访问。不要让网页试听或其他调用意外改变聊天侧的重复历史。

## 用户的文字与语音偏好

偏好应绑定可信事件中的当前发送者；群里其他人的话、引用、转述、历史及假设不应改变其设置。明确要求文字可暂停语音，明确要求语音可恢复；持续时间、累计策略和跨群/私聊共享范围由部署者选择并向用户说明。明确恢复后不应被旧暂停提示覆盖。

如果正常聊天模型支持结构化输出，可以在同一次回复中附带内部媒介意图，并要求其引用当前消息中的原文证据；适配层校验后剥离内部字段，再生成用户可见回复。明确指令可保留规则兜底；模型输出缺失、证据不匹配或意图不确定时，不应持久化猜测。普通“说一下原因”也不必然是语音请求。此方案需要配套适配，不是所有模型或框架默认支持。

## 验收与升级

| 层次 | 示例检查 | 不能据此推断 |
| --- | --- | --- |
| 逻辑与模拟 | 规范化、用户隔离、取消、队列、重试、质量门和种子边界 | 真实模型或平台已经通过 |
| 实际合成 | 冷/热启动、不同长度、有效 WAV、故障回退、资源释放 | 音色满意、逐字完整或接收端收到 |
| 听验 | 固定文案、多个条件与种子的盲听、内容和问题分类 | 所有文案和真实环境都可靠 |
| 消息端到端 | 经授权的测试账号确认实际接收、播放及回退 | 未来升级后依然通过 |

升级前备份相应代码、配置、模型及必要数据；等待队列排空，记录正在运行的版本与权重。逐项部署并验证实际加载路径、健康、冷启动和合成，最后按授权测试消息；回滚应针对本次变更文件并保留之后新增的数据。热重载接口超时不等于成功或失败，应核验运行中实例和加载的版本。不要将健康检查、模拟发送和真实接收混成同一项验收。
